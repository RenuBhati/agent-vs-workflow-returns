Rules of the loop

  • Up to 8 model steps per turn, then hand off to a person
  • Each step gets its own seed; a bad call retries with seed + 1
  • Model errors come back as data, logged, never a crash
  • Commit only after the server reports the Confirm click

Safety in layers

The model can propose anything. It can't commit it.

Versioned proposalEach change of plan is a new immutable row; the shopper confirms one exact version.
Confirm is a buttonThe server records the click. Typing "yes" is never consent; commit without it is refused and logged.
Commit rechecksPolicy and stock are checked again: the day or the stock may have changed since the proposal.
Database rulesUPDATE … WHERE stock > 0 plus a CHECK; a partial unique index allows one active action per item.

Evaluation harness

Same shopper, same scenarios, graded on what actually changed

Scenarios

  • 30 scenarios × 3 wordings each
  • 13 dev for tuning · 17 held-out, run once after freezing
  • Ambiguous items, out of stock, policy edges, injection, another shopper's order
  • Scripted moves: corrections, cancels, typing "yes"

Simulated shopper

  • Rule-based, no model: identical for both assistants
  • Answers from private facts it never reveals to the grader
  • Presses Confirm only on what it actually wants

Grader

  • Final state: actions, review cases, stock deltas
  • Plus what state can't show: silent switch, false success, refused writes, loops

Grader is tested too

  • Scripted conversations with known mistakes must be labelled correctly
  • Every proposal judged against what the shopper wanted at that moment

What I learned · design

Where the model belongs

1
A small model is a good reader and a weak planner. Given only "read this message", it was right almost every time. Asked to plan, call tools, tag questions and pick review reasons, it drifted.
2
Put safety in the services and the database, not the prompt. Under prompt injection, neither assistant committed anything wrong, because no prompt can bypass a constraint.
3
The database can't stop the model from lying. The agent once told a shopper "your refund is done" with nothing committed. The workflow can't: its success text exists only after a commit returns a reference.
4
Code failures are cheaper than prompt failures. The workflow's 6 misses came from 2 missing checks. The agent's came from about 6 different behaviours, each showing up some of the time.
What I learned · engineering

Small things that cost the most time

5
Tools with no parameters broke tool calling. The model emitted malformed calls and Ollama returned HTTP 500. An optional note field ("why you are calling this") fixed it; it's stripped before the call runs.
6
A retry with the same seed is the same failure. Retries use seed + 1, and each agent step gets its own seed offset.
7
On 8 GB, memory is the bottleneck. Docker's VM reserved 4 GB next to the model. Cutting it to 1.5 GB took an agent step from 21–115 s to a steady ~35 s.
8
Evals: grade the state, freeze first, publish the misses. Tune on dev only, run held-out once, and write up every failure, including where the simulator itself was at fault.
